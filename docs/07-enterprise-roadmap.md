# JMQX 企业级路线图（12 周）

本文档用于指导 JMQX 从“可用原型”演进到“企业级可交付产品”。

## 1. 目标与范围

### 1.1 总体目标
- 形成可复制部署、可观测、可运维、可扩展、可审计的 MQTT 平台能力。
- 建立稳定的工程流程（质量门禁 + 性能回归 + 发布规范）。

### 1.2 里程碑周期
- P0：第 1-4 周（可上线）
- P1：第 5-8 周（企业可用）
- P2：第 9-12 周（企业增强）

## 2. P0（第 1-4 周）：可上线基线

### 2.1 核心工作
- 稳定性基线
- 补齐 QoS1/QoS2、Retained、Will 的崩溃恢复与重启恢复用例。
- 建立 72h 长稳压测（连接稳定、消息链路、资源曲线）。
- 过载保护
- 完成连接/订阅/发布限流参数化与默认值收敛。
- 统一拒绝行为、错误码与日志字段。
- 可观测性最小闭环
- 暴露 Prometheus 指标（连接数、消息吞吐、失败数、队列积压、P99 延迟、GC）。
- 配置基础告警规则与阈值说明。
- 运维交付
- 提供 Docker 镜像、基础 Helm Chart、生产参数模板（2C4G/4C8G）。
- 输出标准化启动、停机、回滚 SOP。
- 安全最小闭环
- 管理端登录鉴权与操作审计日志落地。
- TLS 开启与证书配置文档完善。

### 2.2 验收标准（DoD）
- 72h 长稳无崩溃、无持续积压。
- 核心指标可观测且能告警。
- 具备“可部署 + 可回滚 + 可排障”的运维手册。

## 3. P1（第 5-8 周）：企业可用

### 3.1 核心工作
- 集群可靠性演练
- 覆盖 leader 切换、节点下线、网络抖动、重连风暴场景。
- 输出故障演练报告（恢复时间、影响范围、处置步骤）。
- 管理面增强
- 配置变更校验、变更审计、回滚能力。
- 节点健康、容量与热点看板。
- 性能工程体系化
- 固化压测场景并接入 CI（回归阈值门禁）。
- 每次发布产出性能回归报告。
- API 治理
- 管理 API 版本化、错误码规范、幂等约定与分页过滤规范。
- 安全加固
- RBAC 细粒度权限。
- 敏感配置加密存储与脱敏输出。

### 3.2 验收标准（DoD）
- 集群关键故障可自动恢复或可流程化恢复。
- 发布前自动产出性能回归结论。
- 管理面配置修改全程可追溯（谁、何时、改了什么）。

## 4. P2（第 9-12 周）：企业增强

### 4.1 核心工作
- 多租户能力
- 租户级连接/订阅/吞吐配额与隔离。
- 生命周期治理
- Retained/Will/Inflight 的 TTL、容量策略、清理策略可配置。
- 可观测性升级
- 引入 OpenTelemetry Trace，打通请求链路追踪。
- 建立 SLO 看板与误差预算管理。
- 灾备与合规
- 跨机房容灾演练（RTO/RPO）。
- 依赖漏洞扫描、License 合规、制品签名与追溯。

### 4.2 验收标准（DoD）
- 多租户资源隔离可验证。
- 关键链路具备 Trace 与 SLO 报表。
- 灾备演练有可审计记录与达标结论。

## 5. 执行节奏（建议）

### 5.1 周节奏
- 周一：目标确认与风险评审
- 周三：中期检查（性能与质量门禁）
- 周五：阶段验收与文档更新

### 5.2 发布节奏
- 双周发布（含回归报告）
- 每月一次故障演练（含复盘）

## 6. 交付物清单（每阶段必须输出）

- 架构图与关键链路时序图
- 压测报告（场景、参数、瓶颈、结论）
- 运维手册（部署、扩缩容、故障处理）
- 安全手册（鉴权、证书、审计）
- 发布说明（变更点、兼容性、回滚方案）

## 7. 风险清单与应对

- 风险：功能迭代挤压性能治理时间
- 应对：把性能回归纳入发布门禁，未达阈值不发布。
- 风险：配置项增长导致运维复杂度上升
- 应对：配置分层 + 默认模板 + 配置校验器。
- 风险：集群场景问题复现困难
- 应对：标准化故障注入脚本与演练模板。

## 8. 建议优先级（当前代码基线）

- 第一优先级：稳定性、可观测性、限流与过载保护
- 第二优先级：管理面审计与配置回滚
- 第三优先级：多租户与容灾合规

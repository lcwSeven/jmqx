# JMQX 最佳实践

## 1. 架构实践

1. 生产优先使用 3 Core + N Replicant 拓扑。
2. Core 与 Replicant 网络尽量同机房低时延部署。
3. Core 使用独立磁盘存放 Raft 数据目录。
4. 明确 Core/Replicant 的接入职责，避免无规划混部。

## 2. 路由与订阅实践

1. 共享订阅组名保持稳定，不要频繁变更。
2. topic 设计避免过深层级和过多通配符。
3. 对高热点 topic 做分组拆分，避免单组拥塞。
4. 订阅变更频繁场景优先观察元数据写入时延。

## 3. 认证与鉴权实践

1. Auth / ACL 插件链路按“命中率高 -> 低”顺序配置。
2. 配置合理缓存时间，避免每条消息都访问外部系统。
3. HTTP 鉴权接口必须设置超时与熔断策略。
4. Redis/DB 鉴权建议使用专用只读账号与最小权限。

## 4. Retained 实践

1. 必须设置 `maxEntries/maxBytes/maxPayloadBytes`。
2. 默认建议使用 `evict_lru`，避免写路径雪崩。
3. 监控 RocksDB 文件增长与磁盘利用率。
4. 对超大 payload 业务建议关 Retained 或限制 topic。

## 5. 共享订阅实践

1. 组内消费者数量建议与业务并发匹配。
2. 开启慢消费者剔除，避免拖垮整组吞吐。
3. 关注 channel `writable` 与排队积压。
4. 多节点场景验证“两级轮询”是否满足业务公平性。

## 6. 集群稳定性实践

1. 将 `nodeDownCleanupDelayMs` 设为大于常见抖动时长。
2. 保证 `coreEndpoints` 配置一致并可达。
3. 对 leader 切换、网络抖动、节点重启做周期演练。
4. 对元数据提交失败建立告警，不要静默忽略。

## 7. 压测实践

1. 先做单机场景基线，再做集群扩展压测。
2. 压测模型尽量贴近真实 topic / payload / 在线时长。
3. 区分连接压测、发布压测、订阅压测、混合压测。
4. 压测期间同步记录 CPU、内存、GC、网络、磁盘指标。

## 8. 发布实践

1. 使用灰度发布：先 Replicant，后 Core。
2. 发布前冻结高风险配置变更。
3. 发布后重点观察 30~60 分钟核心指标。
4. 预置回滚脚本和版本包，确保可快速恢复。

# JMQX 集群故障演练手册

本手册用于验证 JMQX 在真实故障场景下的可用性、一致性与恢复能力。

## 1. 演练目标

验证以下链路：

1. Core Leader 切换后，元数据写入与同步是否恢复。
2. Replicant 断链重连后，元数据是否能追平。
3. 节点下线延迟清理是否按预期生效。
4. 共享订阅在多节点下是否仍保持正确投递。

## 2. 演练准备

推荐环境：

- 3 Core + 2 Replicant
- 至少 1 组共享订阅业务流量
- 有连续 PUBLISH/SUBSCRIBE 流量

演练前采集基线：

- 在线连接数
- Leader 节点标识
- 元数据提交成功率
- Replicant 同步延迟

## 3. 场景 A：Leader 节点故障

步骤：

1. 确认当前 Leader（从日志或管理输出）。
2. 停止 Leader 进程。
3. 持续发起 SUBSCRIBE / UNSUBSCRIBE / PUBLISH。
4. 观察新 Leader 选举并恢复写入。

验收标准：

- 选举时间可控（通常秒级）
- 写请求在切换后恢复成功
- 共享订阅仍可持续收消息

## 4. 场景 B：Replicant 与 Core 断链

步骤：

1. 在 Replicant 节点与 Core 之间注入网络隔离（或停止 Replicant 进程）。
2. 保持业务流量持续写入。
3. 恢复网络或重启 Replicant。
4. 观察 Replicant 重放或快照重建过程。

验收标准：

- Replicant 可自动重连 Core
- 元数据最终追平
- 不出现长期路由缺失

## 5. 场景 C：节点下线清理

步骤：

1. 让某 Replicant 下线。
2. 等待 `jmqx.cluster.nodeDownCleanupDelayMs`。
3. 观察该节点订阅路由是否被清理。
4. 让该节点重新上线，观察是否重新注册路由。

验收标准：

- 延迟窗口内不误删
- 窗口后可清理僵尸路由
- 节点恢复后路由可重建

## 6. 场景 D：共享订阅正确性

步骤：

1. 在多节点上创建同一共享组订阅：`$share/g1/topic/test`。
2. 持续发布 `topic/test`。
3. 观察消息分配是否符合“两级轮询”。

验收标准：

- 不出现明显重复投递异常
- 不出现长期“某节点永远不分配”
- 慢消费者被正确跳过/剔除

## 7. 场景 E：Core 全可用但单 Core 网络抖动

步骤：

1. 仅对一个 Core 注入高时延/丢包。
2. 观察 Replicant 对 Core 的重试与切换。
3. 观察元数据写入成功率变化。

验收标准：

- 请求可转发到可用 Leader
- 抖动 Core 不导致整体不可用
- 业务延迟可恢复到基线范围

## 8. 观察指标清单

- Core：
  - leader/follower 状态变化
  - submit 失败率
  - eventHistory 缓冲大小
- Replicant：
  - lastAppliedLogIndex
  - ACK 间隔和批量
  - 重连次数
- Broker：
  - 连接数
  - 订阅数
  - 发布成功率
  - 共享订阅投递分布

## 9. 演练结论模板

建议每次演练产出记录：

1. 演练场景与时间窗口
2. 关键指标变化
3. 是否通过验收标准
4. 异常与根因
5. 改进项与责任人

## 10. 建议频率

- 每周：至少 1 个单场景演练
- 每月：全链路组合演练
- 大版本发布前：完整回归演练

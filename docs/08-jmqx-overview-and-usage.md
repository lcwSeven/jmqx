# JMQX 功能与使用指南

## 1. JMQX 是什么

JMQX 是一个基于 Java + Netty 的 MQTT Broker，目标是提供一套可读、可扩展、可演进的 Java 版 MQTT 服务端实现。

它面向的不是“只想快速跑一个黑盒 Broker”的场景，而是更适合下面这类团队：

- 团队主技术栈是 Java
- 希望自己掌控 Broker 的实现和运行机制
- 需要对认证、ACL、桥接、管理后台做定制开发
- 需要本地可调试的集群验证环境

如果把它放到一句话里描述，可以理解为：

**JMQX 是一个对 Java 开发者友好的 MQTT Broker。**

## 2. JMQX 能做什么

JMQX 当前已经具备比较完整的 MQTT Broker 基础能力。

### 2.1 MQTT 接入能力

JMQX 支持常见的客户端接入方式：

- MQTT TCP
- MQTT over WebSocket

这意味着它既适合设备直连，也适合浏览器或前端页面通过 WebSocket 方式接入。

### 2.2 Broker 核心能力

在 Broker 运行时能力上，JMQX 已经支持：

- 客户端连接与断连
- 订阅与退订
- 普通订阅路由
- 共享订阅
- Retained 消息
- QoS inflight 存储
- Will 消息持久化

这些能力构成了一个 MQTT Broker 的基础盘，也是 JMQX 可以承载真实连接和消息流量的关键。

### 2.3 插件化连接鉴权

JMQX 的连接鉴权采用插件化设计，不是写死在 Broker 里的。

当前支持的认证方式包括：

- HTTP
- 文件
- Redis
- MySQL
- PostgreSQL
- 内置数据库

同时它支持**链式认证**。也就是说，可以把多个认证源按顺序组合，例如：

1. 先查内置数据库
2. 未命中再查 Redis
3. 再未命中再请求 HTTP

这种方式非常适合业务系统逐步演进时的过渡场景。

### 2.4 插件化 ACL 鉴权

除了连接认证，JMQX 还支持 Topic 级别的 ACL 鉴权。

当前 ACL 同样支持链式配置，可以组合：

- 文件 ACL
- Redis ACL
- HTTP ACL

这让客户端的发布、订阅行为可以按业务需要做更灵活的访问控制。

### 2.5 内置数据库用户管理

JMQX 当前已经支持“内置数据库”认证模式，并且在管理后台中可以直接维护用户。

支持的能力包括：

- 添加用户
- CSV 导入用户
- 删除用户
- 按 `username` 或 `clientId` 作为账号类型
- 配置密码哈希算法
- 配置加盐方式
- 配置超级用户

其中“超级用户”认证通过后可以绕过 ACL 鉴权，这对运维账号、系统账号会比较实用。

### 2.6 黑名单与客户端运维

管理后台已经支持对在线客户端进行运维控制：

- 查看客户端列表
- 踢下线
- 按 `clientId` 拉黑
- 按 IP 拉黑

这些能力对排查异常设备、错误连接风暴、恶意来源会很有帮助。

### 2.7 消息桥接

JMQX 还支持将消息桥接到外部系统。

当前支持的桥接目标包括：

- Kafka
- RocketMQ
- MySQL

桥接配置支持：

- 全局 Topic Filters
- 每个桥接器独立配置
- 每个桥接器单独启用或停用
- 每个桥接器配置自己的目标 Topic、表名、连接参数

这让 JMQX 不只是一个设备接入 Broker，也可以作为消息中转层接入企业内部数据平台。

### 2.8 内嵌管理后台

JMQX 自带一个内嵌管理页面，不依赖单独前端部署。

当前后台主要支持：

- 集群概览
- 客户端列表
- 黑名单
- ACL 鉴权
- 连接鉴权
- 内置数据库用户管理
- 桥接配置

对于本地调试、测试环境和中小规模部署来说，这种内嵌式管理体验会非常直接。

## 3. JMQX 的架构特点

JMQX 的一个关键设计，是采用 **Core / Replicant** 集群模型。

### 3.1 Core 节点

Core 节点主要负责：

- 元数据写入入口
- Raft 共识复制
- 订阅、路由等元数据同步
- 向其他节点广播元数据变化

### 3.2 Replicant 节点

Replicant 节点主要负责：

- 承载大量客户端连接
- 维护元数据只读副本
- 接收 Core 下发的同步事件
- 处理本地消息收发

简单理解：

- `Core` 更像大脑
- `Replicant` 更像连接层和执行层

这种设计很适合物联网和大连接场景，因为连接压力和元数据一致性压力可以拆开处理。

## 4. 为什么它对 Java 团队友好

相比很多非 Java 生态的 Broker，JMQX 对 Java 团队有几个天然优势。

第一，技术栈统一。  
如果团队本身就熟悉 Java、Netty、Maven、MySQL、Redis，那么理解和调试 JMQX 的成本会更低。

第二，二次开发门槛低。  
你可以比较自然地扩展：

- 新的认证插件
- 新的 ACL 数据源
- 新的桥接器
- 管理后台接口
- 运维控制能力

第三，工程结构清晰。  
模块边界比较明确：

- `jmqx-core`：Broker 核心
- `jmqx-cluster`：一致性与同步协议
- `jmqx-transport`：网络接入层
- `jmqx-plugin`：Auth / ACL / Bridge 插件
- `jmqx-app`：启动装配与管理后台

## 5. 如何快速上手

### 5.1 环境要求

- JDK 17
- Maven 3.9+

### 5.2 编译项目

```bash
mvn -DskipTests compile
```

### 5.3 启动 Broker

```bash
mvn -pl jmqx-app -am exec:java
```

默认入口：

- MQTT: `127.0.0.1:1883`
- WebSocket: `ws://127.0.0.1:8083/mqtt`
- Admin: `http://127.0.0.1:18081/admin/`

### 5.4 登录管理后台

在本地集群脚本默认配置下，管理后台账号密码是：

```text
admin / public
```

这组账号更适合本地调试环境，生产环境建议及时修改。

## 6. 如何体验本地集群

JMQX 已经提供了一套本地集群脚本，默认可以快速拉起：

- 3 个 Core
- 2 个 Replicant

启动：

```bash
./scripts/local-cluster/start-all.sh
```

查看状态：

```bash
./scripts/local-cluster/status.sh
```

停止全部：

```bash
./scripts/local-cluster/stop-all.sh
```

默认管理后台地址：

```text
http://127.0.0.1:18081/admin/
```

这套脚本适合验证：

- Raft 选主
- Core / Replicant 分工
- 集群概览聚合
- 跨节点消息路由
- 黑名单同步
- 鉴权配置同步
- 桥接配置同步

## 7. 适合哪些场景

JMQX 比较适合下面这些场景：

- Java 团队自建 MQTT 服务端
- 需要深度定制认证、ACL、桥接逻辑
- 需要本地可调试的 MQTT 集群环境
- 需要在 Broker 层直接对接 Kafka、RocketMQ、MySQL 等外部系统

## 8. 总结

JMQX 当前已经不是一个“只能演示连接和收发消息”的简单项目，而是具备了一套比较完整的 MQTT 服务端骨架：

- 有接入能力
- 有会话和路由
- 有认证和 ACL
- 有桥接
- 有管理后台
- 有集群模型
- 有本地验证脚本

对于希望在 Java 生态内建设 MQTT 基础设施的团队来说，它既适合作为学习 Broker 的切入点，也适合作为一个可以继续演进的工程基础。
